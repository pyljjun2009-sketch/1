# ADR-003：事务式 Profile 恢复与升级操作串行化

## 状态

已采纳（2026-09）

## 背景

DSH Desktop 会直接管理 `~/.dsh/profiles/web` 的关键配置、插件依赖和恢复备份。
这些操作与正在运行的 `dsh web` 共享同一目录，存在四类高风险失败模式：

- 损坏或被篡改的备份在未校验时覆盖当前可用 Profile；
- 逐文件删除、写入过程中失败，留下半恢复状态；
- 后端仍在读取 Profile 时执行目录替换或清理 `node_modules`，导致文件锁和状态不一致；
- 用户重复点击升级按钮，造成同一升级轨道并发执行 npm/plugin 操作。

本项目是单用户桌面宿主，不需要分布式事务，但要求恢复失败时当前数据可回滚、
升级过程可解释，并优先避免数据丢失和孤儿进程。

## 决策

1. 每份新备份的 manifest 使用与落盘文件完全相同的单次快照，并记录完整 SHA-256。
2. 恢复前校验 manifest、允许文件集合、文件存在性和内容摘要；兼容旧版 12 位摘要。
3. Profile 恢复先在同一磁盘卷创建完整暂存目录，再通过目录重命名切换：
   - 当前 `web` 目录先改名为 rollback 目录；
   - 暂存目录切换为新的 `web`；
   - 任一步失败时尽力恢复 rollback 目录和原 `settings.yaml`；
   - 成功后再删除 rollback 目录。
4. 设置页发起恢复时，若后端正在运行，必须按“停止后端 → 恢复 → `plugin install`
   同步依赖 → 启动后端”的顺序执行。
5. 同一升级轨道同一时间只允许一个 apply 操作；重复请求明确返回“正在进行”。
6. Profile bundle 更新成功后自动重启后端，不再把关键收尾步骤留给用户。

## 后果

### 正面

- 被篡改、缺文件或路径异常的备份会在改动当前 Profile 前被拒绝。
- 大多数磁盘写入失败不会留下半写入目录，恢复前自动备份仍可人工兜底。
- 恢复后的 bundle 声明、`node_modules` 与运行中后端保持一致。
- 多次点击升级不会并发修改全局 npm 安装或 Profile。
- 失败结果包含阶段和恢复前备份 ID，便于诊断与手工回滚。

### 负面

- 恢复时需要同卷额外空间保存暂存目录和短期 rollback 目录。
- `plugin install` 与后端重启会让恢复操作耗时更长。
- Windows 上若外部进程占用 Profile 文件，目录重命名仍可能失败；此时操作会返回错误并保留恢复前备份。

### 中性

- V1 备份仍为明文；本 ADR 解决完整性与恢复原子性，不解决静态加密。
- 全局 `settings.yaml` 与 Profile 目录无法组成真正的文件系统级跨路径事务，使用内存快照和恢复前备份补偿。

## 备选方案

**继续逐文件覆盖**

- 拒绝：实现简单，但删除或写入中断会造成半恢复状态，无法满足数据安全目标。

**把完整 `node_modules` 一并备份**

- 拒绝：体积大、复制慢，并可能恢复与当前 Node/DSH 版本不兼容的原生依赖。
- 当前选择是恢复关键声明后重新运行 `dsh plugin install`。

**允许并发升级，由 npm/pnpm 自行加锁**

- 拒绝：不同工具的锁语义不一致，错误提示不清晰，且可能同时触发多次后端重启。
